# CarbonLab OPC 项目交接说明

## 1. 当前状态

项目处于“P0 最小闭环已迁移并通过合成数据工程验证，等待赛事平台开展真实验证”的阶段。

它可以演示：文件进入系统后，AI 提出候选，人确认数据，确定性代码完成计算，系统生成可追溯、可重放的护照版本。

它尚不能证明：模型适用于真实客户、报告具备法定效力、产品已经完成商业验证。

## 2. 当前可运行流程

1. 创建本地演示用户和两条护照路径；
2. 登录 `/login`；
3. 在 `/upload` 上传 PDF、CSV、XLSX 或文本文件；
4. 查看规则解析或 AI 候选；
5. 人工确认、修改或拒绝；
6. 已确认数据进入正式活动/结果链；
7. 在 `/passports` 查看装置、期间、输出、归集、SEE、证据和完整度；
8. 形成草稿，完成人工方法复核；
9. 发布不可变版本并检查重放；
10. 创建最小授权，导出限定字段包并留下分发记录。

## 5. 环境与外部依赖

- 必需：Python 3.12 或 Docker、Node 22、PostgreSQL 16；
- 可选：OpenAI-compatible LLM；
- 可选：MinIO；默认使用本地存储；
- 当前最小流程不要求 Redis/Celery；
- 模型 API Key 只放本地 `.env`，不得提交。

## 6. 已知缺陷和技术债

1. 前端 AuthContext 有 1 条 Fast Refresh lint warning；
2. 数据库历史迁移包含未暴露业务的旧表；未来可在独立决策后做 schema squash，本轮不重构；
3. 文件解析对复杂扫描件、合并单元格和低质量 OCR 的覆盖不足；
4. 当前字段集合仍需由人类冻结为 6—10 个复赛核心字段；
5. 证据位置在不同文件格式间的统一表达需要真实样本验证；
6. 当前模型登记均无效，不能用旧报告做上线依据。

## 7. 后续优先级

P0（第一周）：冻结一个虚拟工厂、一个装置、一个产品、一个期间和 6—10 个字段的独立标准答案。

P1：用现有 Candidate 做开发，用 Holdout/Adversarial 做盲测，修复字段-证据错配和缺失值诚实性。

P2：组织 3—5 名非专业用户完成上传、确认、发布任务，记录时长、错误和求助点。

P3：在人类批准后接入一批已脱敏真实文件，只做影子测试，不自动写正式账本。

## 8. 必须由人类批准

- 核心字段和方法学版本；
- Candidate/Holdout/Adversarial 的最终冻结；
- 模型 Provider、版本和资格结论；
- 真实企业文件接入；
- 护照对外发布和分享对象；
- 任何“合规、核查、监管认可”表述；
- GitHub 可见性和协作者权限。

## 9. 不能对外宣称

- 已服务真实客户或已完成付费试点；
- 已通过 CBAM、CMA、CNAS 或监管认证；
- AI 可以独立完成核算和发布；
- 历史 DeepSeek 报告仍然有效；
- 合成数据准确率等同真实企业准确率；
- 本系统替代核查机构或法定签字人。
