# OPC 赛事平台接管说明

## 1. 唯一基线

后续复赛深化只以 GitHub 仓库 `Ghostsci/carbonlab-opc` 的 `main` 分支为基线。旧 Codex 项目只作为历史来源，不再继续复赛业务开发。

## 2. 接管阅读顺序

1. `README.md`：用通俗语言理解产品；
2. `docs/handoff/project-handoff.md`：确认真实完成度；
3. `docs/handoff/feature-status-matrix.md`：逐模块看状态；
4. `docs/architecture/system-architecture.md`：理解 AI、人和确定性代码边界；
5. `docs/handoff/runbook.md`：启动与验证；
6. `validation/PRODUCT_VALIDATION_PROTOCOL.md`：验证方法；
7. `ai/memory-bank/tasks/master-plan.md` 和 `week-01.md`：开始执行。

## 3. 首先创建的赛事平台项目

建议项目名称：

**零碳云 CarbonLab｜AI 原生制造企业碳数据提取、核算与可信护照系统**

首个里程碑：

**冻结单一虚拟制造企业的 6—10 个核心字段、独立标准答案和验收任务。**

不要把“继续优化 UI”设为第一任务。

## 4. 8 名数字员工建议分工

实际账号名称待人类确认，职责建议如下：

1. 项目协调员：范围、周报、决策和风险；
2. 行业问题分析员：制造业流程和字段定义；
3. 数据管理员：数据集拆分、去重、版本和标准答案；
4. AI 工作流工程师：操作契约、Provider 和候选提取；
5. 证据审查员：字段—证据一致性和失败案例；
6. 后端工程师：状态约束、计算、账本和 API；
7. 前端/可用性工程师：非专业用户任务和界面；
8. 测试发布工程师：测试、迁移、构建和阶段门。

## 5. 6 个虚拟专项组建议

| 专项组 | 组成 | 职责 |
|---|---|---|
| G1 范围与产品组 | 1、2、7 | 字段、用户任务、验收边界 |
| G2 数据与金标组 | 2、3、5 | 虚拟工厂、数据集、独立答案、证据 |
| G3 AI 提取组 | 3、4、5 | 契约、模型比较、错误分类 |
| G4 核算与证据组 | 2、5、6 | 单位、规则、计算、重放 |
| G5 工程交付组 | 6、8 | API、数据库、CI、部署和留痕 |
| G6 可用性与验证组 | 1、7、8 | 非专业用户测试和阶段验收 |

## 6. 第一项任务

交给 **G2 数据与金标组**：

> 在不修改模型和产品代码的前提下，冻结一个虚拟制造企业、一个生产装置、一个产品、一个报告期间及 6—10 个字段；为每个字段给出独立标准值、单位、证据位置、允许缺失规则和拒绝条件，并形成 Candidate/Holdout/Adversarial/Usability 四类任务清单。

原因：没有可信标准答案，模型准确率、产品价值和 UI 好坏都无法科学判断。

## 7. 当前仍需人类批准

- 核心字段和业务口径；
- 方法学和规则版本；
- 数据集冻结；
- 模型 Provider、模型名称和预算；
- 模型资格结论；
- 真实企业数据使用；
- 护照发布和对外分享；
- GitHub 协作者和仓库可见性；
- 对外宣传中的“合规、核查、认证”措辞。

## 8. 批准前不得开始

- 不得接入真实企业敏感文件；
- 不得将 LLM 输出自动写入正式账本；
- 不得创建新的有效 `QUALIFICATION_LOCK.json`；
- 不得宣称任何模型已通过生产准入；
- 不得扩展碳交易、绿证、金融或监管申报功能；
- 不得把 DEMO 数据描述为客户案例；
- 不得把系统描述为第三方法定核查替代品。

## 9. 周度留痕

每周至少提交：

1. 本周新增问题；
2. 本周验证假设；
3. 使用的数据集版本；
4. AI 工作流变更；
5. 人类审批记录；
6. 失败案例；
7. 测试命令和实际结果；
8. 下一周阶段门。

记录放入 `ai/memory-bank/tasks/week-XX.md`，关键决定追加到 `decision-log.md`。

## 10. Codex 停止边界

本次迁移和交接完成后，Codex 不再继续复赛业务功能开发，不新增页面、不调整模型、不生成正式评测结果，等待赛事平台按上述结构接管。
